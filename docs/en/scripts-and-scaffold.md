# Scripts and Scaffold

## Available scripts

| Script | Purpose |
|--------|---------|
| `create_environment.sh <env>` | Creates `live/<env>/` with `environment_vars.yaml` and a minimal `terragrunt.hcl` |
| `create_environment_datacenter.sh <env> <dc>` | Creates `live/<env>/<dc>/` with `datacenter_vars.yaml` and a minimal `terragrunt.hcl` |
| `create_environment_stack.sh <env> <dc> <stack> [vm\|ct]` | Creates a stack with `stack_vars.yaml` and a stack `terragrunt.hcl` including `root`, `providers`, and the right `_envcommon` file |
| `checks_sre.sh [--fast]` | Anti-regression checks for architecture, wiring, defaults, formatting, backend behavior, and fixture validation |
| `audit_state.sh` | Read-only audit of stack state layout, stray state files, and cache leftovers |

Internal helpers:

- `scripts/lib_envcommon.sh` bootstraps and validates `live/_envcommon/`
- `scripts/lib_yaml.sh` centralizes YAML parsing and normalization for scaffold scripts

These helpers are sourced by the public entrypoint scripts. They are not intended to be run directly.

## Scaffold workflow

From the repository root:

```bash
./scripts/create_environment.sh demo
./scripts/create_environment_datacenter.sh demo lab-01
./scripts/create_environment_stack.sh demo lab-01 vm-demo vm
```

Then configure Proxmox access locally and work from the stack directory:

```bash
cd live/demo/lab-01/vm-demo
terragrunt init -upgrade
terragrunt validate
terragrunt plan -out=tfplan
```

`terragrunt init` downloads providers from the registry, so local runs and CI need outbound connectivity unless a plugin mirror or cache is configured.

The generated YAML files are starting points. Review and adapt them to your cluster before the first `plan`.

To audit the resulting state layout:

```bash
bash scripts/audit_state.sh
```

## Supported flags and naming rules

- scaffold scripts accept `--force`
- scripts that support previews also accept `--dry-run`
- environment, datacenter, and stack names must match `^[a-z0-9-]+$`

`--dry-run` does not bypass layer dependencies:

- `create_environment_datacenter.sh` still requires an existing environment
- `create_environment_stack.sh` still requires an existing environment and datacenter

### `datacenter_short` derivation

`create_environment_datacenter.sh` writes `datacenter_short` into `datacenter_vars.yaml` using these rules:

- names ending in `-NN` derive `dcNN`
- other names are compacted to lowercase alphanumeric characters and truncated to four characters

That short code becomes part of the instance naming contract.

## `_envcommon` bootstrap

`create_environment.sh` ensures that `live/_envcommon/` exists by copying:

- `templates/envcommon/vm-service.hcl`
- `templates/envcommon/lxc-service.hcl`

The same bootstrap can be forced with `--force`.

If `live/_envcommon/` is missing when creating a stack, `create_environment_stack.sh` attempts to bootstrap it before failing.

## Origin of scaffold defaults

1. `config/datacenter-defaults.yaml` defines canonical datacenter defaults under `proxmox:`
2. `scripts/lib_yaml.sh` reads scalars and lists with `proxmox.*` plus legacy fallbacks
3. `create_environment_datacenter.sh` writes normalized values into `datacenter_vars.yaml`
4. `create_environment_stack.sh` reads datacenter defaults back into `stack_vars.yaml`
5. VM stacks generated by the scaffold write `template`, `template_vm_id`, and `use_clone: true`

Relevant defaults persisted by the scaffold include:

- `default_node`
- `default_bridge`
- `default_storage`
- `default_pool`
- `default_vm_template`
- `default_template_vm_id`
- `default_vm_id_base`
- `default_ct_template`
- `default_ct_id_base`

## Stack presets

`create_environment_stack.sh` generates preset content based on the stack name:

- VM presets: `k8s-masters`, `k8s-workers`, `longhorn`, and the generic `primary` group
- CT presets: `vpn-agent` and the generic `primary` group

The public examples under `live/example/` stay intentionally small and readable. They document the contract, while scaffold generation focuses on producing a usable starting tree.

## Curated examples vs generated scaffold

`live/example/` is a curated public reference tree:

- it matches the current public contracts
- it does not need to be a byte-for-byte copy of scaffold output
- it uses readable sample values such as `datacenter_short: lab01`

The scaffold follows its own deterministic rules. For example, `create_environment_datacenter.sh demo lab-01` derives `datacenter_short: dc01`.

## Public scaffold defaults

A freshly generated VM stack uses these defaults unless you change them first:

- node: `pve01`
- bridge: `vmbr0`
- storage: `local-lvm`
- template: `ubuntu-2404-cloudinit`
- template VMID: `9000`
- VMID base: `4000`

The VM scaffold also enables clone mode by default with `use_clone: true`.

Canonical datacenter defaults keep `default_ct_template: null`.

The public datacenter example sets an explicit CT template so the example CT stack is self-contained:

`local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst`

For generated CT stacks:

- `os_template` is read from `datacenter_vars.yaml`
- if that value resolves empty, the scaffold falls back to the Debian template identifier shown above
- if `datacenter_vars.yaml` explicitly keeps `default_ct_template: null`, that contract still needs a real template before planning

## Strict defaults mode

To force validation of `default_ct_id_base` as a proper integer during datacenter scaffold generation:

```bash
STRICT_DEFAULTS=true ./scripts/create_environment_datacenter.sh demo lab-01
```

For the YAML contract consumed by the scaffold, see [configuration.md](configuration.md).
