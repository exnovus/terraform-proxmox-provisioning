# Architecture

This repository is designed for teams that need reusable Proxmox IaC with clear contracts, predictable naming, and a clean separation between public entrypoints and internal workloads.

## Execution layers

Terragrunt execution is organized in three hierarchical layers:

| Layer | Typical path | Responsibility |
|-------|--------------|----------------|
| `environment` | `live/<env>/` | Global context such as `environment`, `client`, `owner`, naming delimiter, and base tags |
| `datacenter` | `live/<env>/<datacenter>/` | Proxmox defaults such as nodes, bridge, storage, pools, and templates |
| `stack` | `live/<env>/<datacenter>/<stack>/` | Deployable VM or CT unit with `stack_type`, `vm_groups`, or `ct_groups` |

Each layer keeps its own YAML contract and a minimal `terragrunt.hcl`. A stack inherits the environment and datacenter context through `find_in_parent_folders()` and the inputs composed in `_envcommon`.

## Architecture rule: components vs resources

- Terragrunt must only target `modules/components/vm-service`
- Terragrunt must only target `modules/components/lxc-service`
- Terragrunt must never target `modules/resources/proxmox-vm`
- Terragrunt must never target `modules/resources/proxmox-lxc`

The reason is structural, not stylistic. A component orchestrates:

1. `modules/core/tags-manager`
2. the workload module under `modules/resources/*`

That keeps naming, tags, and public contracts consistent across stacks.

## Shared HCL and inheritance

`live/_envcommon/` contains the shared HCL used by all stacks:

- reads `environment_vars.yaml`, `datacenter_vars.yaml`, and `stack_vars.yaml`
- merges tags with null-safe behavior
- resolves `config/proxmox-<env>.hcl`
- sets `terraform.source` to `modules//components/vm-service` or `modules//components/lxc-service`
- passes the full input contract to Terraform modules

The source of truth is `templates/envcommon/`. `live/_envcommon/` is generated by the scaffold and can be recreated with `--force`.

### File resolution rules

- `find_in_parent_folders("environment_vars.yaml", "")` walks up from the stack to find the environment contract
- `find_in_parent_folders("datacenter_vars.yaml", "")` resolves the datacenter contract
- `get_terragrunt_dir()` is used for `stack_vars.yaml`, which is local to the stack

Example from `live/demo/lab-01/vm-demo`:

- `environment_vars.yaml` resolves to `live/demo/environment_vars.yaml`
- `datacenter_vars.yaml` resolves to `live/demo/lab-01/datacenter_vars.yaml`
- `stack_vars.yaml` is read from the current stack directory

## Dynamic Proxmox config resolution

The shared HCL follows this flow:

1. read `environment` from `environment_vars.yaml`
2. look for `config/proxmox-${environment}.hcl`
3. if it does not exist, optionally allow a private local fallback such as `config/proxmox-dev.hcl`
4. if no file exists, keep the config map empty so `validate` can still run
5. prefer runtime environment variables for endpoint and authentication
6. fall back to `https://localhost:8006/` as the effective endpoint when nothing else is defined

Environment variables supported by the public contract:

- endpoint: `PROXMOX_VE_ENDPOINT` or `PM_API_URL`
- token auth: `PROXMOX_VE_API_TOKEN` or `PM_API_TOKEN`
- username/password auth: `PROXMOX_VE_USERNAME` or `PM_USER` plus `PROXMOX_VE_PASSWORD` or `PM_PASSWORD`

The public repository ships `config/proxmox.example.hcl` as a sanitized placeholder. Private local files stay optional.

## Tags and naming

Tags are composed in this precedence order, from lowest to highest:

1. environment tags
2. datacenter tags
3. core tags generated in `_envcommon`
4. stack `custom_tags`

The merged map is passed into the component as `tags`. The component runs `tags-manager`, which:

- normalizes keys and values to strings
- sanitizes them for Proxmox
- exposes `tags_sanitized` and `taglist`

The workload then adds resource-level metadata such as:

- `resource_type`
- `role`
- `group`
- `index`
- `template_os` for cloned VMs

Instance naming follows this pattern:

`{client}-{environment}-{datacenter_short}-{role}-{index2}`

Example:

`example-dev-lab01-app-01`

The default delimiter is `-`, configurable through `naming_delimiter`.

`datacenter_short` comes from the datacenter YAML contract. The public example uses `lab01`, while scaffold-generated values depend on the datacenter name and scaffold rules.

## Execution flow

1. Optional scaffold creates `live/<env>/`, `<datacenter>/`, and `<stack>/`
2. `terragrunt init` resolves includes, backend, provider, and component source
3. `terragrunt validate` checks the generated Terraform configuration
4. `terragrunt plan -out=tfplan` produces a reviewable plan
5. `terragrunt apply tfplan` applies exactly the reviewed plan

## Responsibility diagram

```text
Terragrunt (from live/<env>/<dc>/<stack>)
    -> include root.hcl
    -> include providers.hcl
    -> include _envcommon/vm-service.hcl or lxc-service.hcl
         -> read YAML contracts
         -> merge tags and defaults
         -> resolve Proxmox config
         -> set source to modules//components/*
              -> component runs tags-manager + workload
              -> workload creates Proxmox resources
```

For the YAML-layer contract, see [configuration.md](configuration.md). For the public repository shape, see [repository-structure.md](repository-structure.md).
